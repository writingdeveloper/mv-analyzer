## 1. `talk profile` — 취향 목록 vs 코퍼스 백분위

`compare`가 "목록 안에서 무엇이 공통인가"라면 `profile`은 그 공통점이 코퍼스 128편 안에서 어디에
놓이는지를 붙여 넷으로 가른다.

| 판정 | 조건 |
|---|---|
| 특이점·높음 / 낮음 | 목록 전편이 코퍼스 70백분위 이상 / 30백분위 이하 |
| 공통 | 퍼짐(범위/중앙값) ≤ 0.35이고 백분위 중앙이 극단 |
| 공통·관습 | 퍼짐 ≤ 0.35이지만 백분위 중앙이 30~70 — 목록 안에서 같아도 장르 관습 |
| 무관(편차 큼) | 퍼짐 > 0.35 — 취향이 걸려 있지 않은 축 |

범주형은 목록 쏠림(≥80%)과 코퍼스 비율(<50%)을 함께 봐 "취향 신호 / 관습 / 혼재"로, 색은 씬 길이
가중 색상 버킷(8 hue + 무채색 + 어두움) 분포의 목록 평균 − 코퍼스 평균으로 낸다.

## 2. 씬별 움직임 3분류 (`mva motion-scenes`, `motion_scene_*`)

- 방법: 씬마다 (t, t+0.4s) 프레임 쌍을 최소 3개, 5초당 1개(상한 12) 균등 배치 → 360p Farneback
  flow → 경계 5% 제외 후 크기 평균·분산. 평균 < 0.5 → `static_image`, 분산 < 2.0 → `animated_still`
  (정지 일러스트 위 팬/줌), 그 외 `motion_clip`. 임계값은 OpenMontage가 공개한 360p·0.4s 휴리스틱을
  개념만 빌린 것이며 **사람 라벨 게이트 전엔 가설검정에 넣지 않는다**(`feature_policy` 실험 접두사).
- 구현 메모: 씬마다 seek하면 H.264 재디코딩 때문에 편당 3분 12초가 걸렸고, 필요한 프레임 인덱스를
  모아 한 번의 순차 디코딩으로 회수하도록 바꿔 46초(1080p, 146초 영상)가 됐다. 4K(2160×2160) 영상은
  디코딩 자체가 병목이라 여전히 편당 2분 안팎.
- 합성 검증: 정지 텍스처 / 텍스처 팬 / 텍스처 위 큰 사각형 이동 세 영상에서 세 클래스가 정확히 갈린다
  (`tests/test_motion_scenes.py`).
- 실영상 예비 결과 (코퍼스 배치는 진행 중, `work/experiments/motion/scenes_corpus.jsonl`):

| 영상 | 씬 | static | animated_still | motion_clip |
|---|---|---|---|---|
| 바움쿠헨 엔드롤 자막판 (vF0ZU2GQSzo) | 49 | 0.10 | 0.00 | 0.90 |
| 僕はリーダーになれない (0.3 컷/분) | 2 | 1.00 | 0 | 0 |
| シャボン (0.4 컷/분) | 2 | 1.00 | 0 | 0 |

  풀 애니메이션 MV와 정지 일러스트 MV가 양 끝으로 갈린다. **자막판 vs 원본 대조(같은 날 저녁 확인)**:
  일본 원본 Dz5rALpx06M(자막 없음)은 51씬 · static 0.098 · still 0.0 · clip 0.902 · flow 분산 중앙값
  22.7로, 자막판(49씬 · 0.102 · 0.0 · 0.898 · 20.1)과 사실상 동일하다. 하단 하드섭이 분류를 흔든다는
  우려는 기각 — 경계 5% 제외와 자막 띠의 작은 면적 덕분이다. 바움쿠헨은 실제로 씬의 90%가 움직이는
  풀 애니메이션이고, `animated_still` 0은 측정 오류가 아니다. 남은 한계: 가사 타이포그래피가 화면
  전체인 MV에서는 텍스트 전환이 `motion_clip`으로 잡힌다.

## 4. 제작 브리지 — `talk export` → `openmontage-reference-lab --from-analysis`

- `mv_analyzer/blueprint_export.py`가 `data/<id>/`를 OpenMontage `VideoAnalyzer` 출력 형식으로 변환한다.
  씬 경계·키프레임(씬당 1장, 절대경로)·씬별 transcript(가사 라인)·에너지 수준·모션 분류에 더해,
  씬마다 `mv_analyzer` 필드(색·밝기·인물 수·샷 타입 힌트·컷-비트 오프셋), 전체 `rhythm_profile`,
  `beat_grid_s`, `visual_profile`, `lyrics_profile`을 싣는다. 출력은 `work/exports/`(gitignore).
- 5요소(subject / subject_motion / scene / spatial_framing / camera)는 **의도적으로 비운다.** VLM 태그는
  손실 압축이라(mv-talk 원칙 2) 힌트로만 넘기고, reference-lab이 `VISION ENRICHMENT REQUIRED`로 표시한
  뒤 에이전트가 키프레임을 직접 보고 채우는 기존 흐름을 탄다.
- reference-lab 쪽에는 `analyze --from-analysis <json>`을 추가했다(로컬 커밋 1cb20ef). OpenMontage를
  실행하지 않고 normalize → blueprint → provider prompt(H3 검증) → 리포트까지 기존 단계를 재사용한다.
- 실행 확인: 바움쿠헨 49샷 → 키프레임 49장 복사, `h3-validation.json` 49샷 전부 `H3_DRAFT`
  (정상 — 의미 채우기 전), 2초 안팎 샷은 H3 최소 4초로 생성 후 트림하도록 표시됨.
- 두 저장소는 JSON 한 장으로만 만난다. 코드 import가 없으므로 AGPL 경계가 유지되고, mv-analyzer의
  라이선스 선택지는 그대로 남는다.

### 6편 프로파일 — 리듬 축은 전부 '무관', 남는 것은 정서와 색

n=2에서 보이던 "라우드니스 상위 · 짧은 길이" 특이점은 6편에서 사라졌다. 수치 17개 중 16개가
**무관(편차 큼)**이다: 길이 1:53~4:30(6~96백분위), 분당 컷 14.9~44.3(28~97백분위), 라우드니스
6~88백분위, 비트 정렬 컷 10~75백분위. 즉 이 취향은 **편집 리듬·길이·음압 어디에도 걸려 있지 않다.**

살아남은 신호는 범주형과 색이다.

| 신호 | 목록 | 코퍼스 |
|---|---|---|
| 가사 정서 긍정 | 83% (5/6) | 45% |
| 지배적 무드 활기 | 83% (5/6) | 46% |
| 가사 주제 사랑 | 50% (3/6) | 12% |
| 색 팔레트 | 파랑 +5%p · 청록 +3%p · 무채색 +3%p | 주황 −6%p |

여기에 목록 밖의 사실 하나: 6편 전부에 같은 청록 트윈테일 캐릭터가 있다. 데이터가 말하는 취향의
윤곽은 "빠른 편집"이 아니라 **밝고 긍정적인 정서 + 사랑 주제 + 파랑·청록 계열 + 특정 캐릭터**다.
n=6은 여전히 프로파일이지 통계가 아니며, 코퍼스 백분위에는 이제 이 6편 자신이 포함된다(132편).

### [탐색·일부 철회] 연구 표본 상·하위 그룹의 모션 분포

> **2026-09-03 갱신**: 사람 라벨 게이트 결과 `정지 이미지 씬 비율` 행은 철회, `실제 움직임 씬 비율`은 하한으로만 유효하다. §7.2 참조.


배치가 끝난 김에 보컬로이드 사이클 1 표본(top 25 / bottom 25)에 대고 봤다. **가설검정에 편입하지
않은 탐색치**이며(`feature_policy` 실험 접두사 규칙), 4개 지표를 동시에 봤으므로 FDR 보정 전 p값이다.

| 지표 | top 중앙값 | bottom 중앙값 | Cliff's δ | p (미보정) |
|---|---|---|---|---|
| 실제 움직임 씬 비율 | 0.812 | 0.571 | +0.33 | 0.045 |
| 정지 이미지 씬 비율 | 0.146 | 0.364 | −0.37 | 0.026 |
| 정지 일러스트+카메라 비율 | 0.011 | 0.000 | +0.29 | 0.043 |
| 실제 움직임 시간 비율 | 0.846 | 0.781 | +0.18 | 0.28 |

방향은 §5.3의 제작 투자 프록시 가설과 일치한다(뜬 MV일수록 정지 씬이 적다). 효과 크기는 게이트 문턱
(|δ|≥0.33)에 걸쳐 있고 p는 FDR을 통과하지 못할 크기다. 정식 채택 경로는 기존 규칙대로: ① 사람 라벨
소표본(정지/카메라/피사체)으로 분류 정확도 게이트 → ② 사전등록 후 K-pop·중간층 표본 포함 재검정.
지금 단계에서 인기 요인이라고 말하지 않는다.

### 7.3 점검에서 나온 것 — 프롬프트는 깨끗한데 참조 이미지가 더러웠다

§7.1을 끝내고 산출 폴더를 열어 키프레임과 서술을 대조하다 빠뜨린 것을 찾았다.
**H3의 I2VA는 이미지를 첫 프레임으로 쓴다.** 서술에서 자막 띠를 아무리 지워도 참조 이미지에
팬자막과 검은 띠가 박혀 있으면 생성물이 그대로 물고 들어간다. 실제로 자막판 키프레임 49장 중
**29장에 좌우 240px 필러박스**(1920 → 1440, 정확히 4:3)가 있었고, 한국어 자막도 그대로였다.
값이 23인 진회색이라 "검정" 기준 검출기로는 0장으로 나온다 — 중앙값 대비 비율로 봐야 잡힌다.

`mva gen-frames`로 고쳤다. 같은 곡의 **무자막 일본 원본**(Dz5rALpx06M, 길이 146초로 동일)에서
자막판의 씬 중간 시각으로 프레임을 다시 뽑고, 필러박스를 깎는다. 프레임 번호가 아니라 시각으로
맞추는 이유는 두 판본의 fps가 다를 수 있어서다.

결과: 팬자막(어차피 때는 늦었어 / 피의 축제 / 쪼개서 빼앗아 가는 NTR)은 사라지고 **MV 자체의
일본어 타이포그래피(どうせ後の祭り / 血祭り / 割って·奪って·NT)는 남는다.** 이게 정확히 원하던
분리다 — 팬자막은 업로드본 산물이고 일본어 타이포는 이 MV의 연출이며, 후자는 §7.1의
`--typography abstract`가 프롬프트 층에서 따로 다룬다. 최종 20장 16:9 · 29장 4:3.

`talk export --keyframes`로 이 세트를 꽂아 재실행: H3 ready 49/49, 커버리지 1.0, 참조 이미지 결손 0.
산출은 `output/mv-analyzer-gen/20260903-094719/`로 갱신됐다.

부수적으로 두 가지가 더 잡혔다.
- **어두운 프레임을 1/3 잘라내는 버그**: 화면 전체가 어두우면 모든 열이 임계값 아래라 가장자리
  탐색이 상한까지 간다. 이 MV에는 검정 카드 샷이 있어 실제로 밟을 수 있는 경로였다(테스트가 잡음).
- **`--keyframes`가 video_id 마스킹에 삼켜지던 버그**: 마스킹 정규식이 `-` + 10자라 정확히 11자인
  `--keyframes`가 걸렸다. 둘째 글자가 `-`면 제외하도록 고쳤고 두 CLI에 회귀 테스트를 붙였다.
  2026-09-02의 `lstrip` 버그와 같은 계열 — 하이픈 id를 옵션에서 숨기는 장치가 옵션을 잡아먹는다.
